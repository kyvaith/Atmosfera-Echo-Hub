# Optional Climate Range1

HA126 extends the existing Climate Detail/App6 session with a paired target
facet. It does not implement a thermostat controller or hysteresis. The product
may opt into the feature; missing optional APIs retain the existing read-only
low/high observations and all legacy controls.

`entity_detail_range_query` and `entity_detail_range_bind` negotiate
`entity_detail_range_v1/range_version:1` only after Climate Detail1 is bound on
the same channel/client/connection epoch. Range and Color binding are independent;
Detail rebind or disconnect clears both. Range uses capability bit128 and the
explicit native facet10, including builds without Color. The old Detail
handshake is unchanged. No Extra profile, queue, task, timer or framebuffer is
added by the HA adapter.

Range metadata requires the actual Climate feature2 and live set_temperature
service, explicit positive step, bounded numeric_steps_v1 domain and matching
Core11 native_temperature_unit, HA temperature unit and published temperature_unit.
Core converts published temperatures but leaves target_temp_step unconverted,
so this first adapter deliberately excludes cross-unit control. The source is
the two published target_temp_low/high attributes; stale native getters or
current_temperature cannot supply a missing target. Both must be exact ordered
indices in one domain. Unknown/off-grid pairs are wholly unknown. Zero indices,
zero temperatures and low==high remain valid. Only heat_cool edits; other known
modes retain read-only observations. Missing metadata removes Range support.

The active range facet carries one domain, both indices, mode, activity,
current_text, editable and a bounded reason. Only one facet is retained. A local
lower/upper selector reuses the existing thermostat arc input; pointer release
submits one absolute pair. Entry, selection, Back, unchanged and canceled input
submit no services. Authoritative pair/mode/preset changes invalidate input;
measurement/activity changes do not. The preset signature preserves absent/null
and raw changes even if no preset catalogue is available.

The exact facet_range command contains only target_low_index/target_high_index
plus the established identity, view and expected semantic generation. The same
authorization, lease, deduplication, one pending command and final scheduled
dispatch fence remain authoritative. HA resolves both indices and calls once
`climate.set_temperature` with both targets. It never adds HVAC mode, power or a
single temperature. state_matches requires a newer source generation, both exact
targets, unchanged metadata and the captured mode/preset; partial/rounded feedback
remains unconfirmed and never triggers a retry. Service acceptance does not prove
physical heating/cooling.

The separate owned demo provider delta only sets an explicit step0.5 on its
existing climate_3/climate_presets simulation. It does not change target values,
preset, mode, identifiers or the single-target mock. This provider file is a
separate deployment boundary from the Atmosfera integration package.

The agreed design and proposed examples are in
`C:/aeh-build/thermostat-range104-work/contract.md`; the implementation corpus is

Host evidence, native compile, deployment, screenshots and physical actuator
behavior are separate claims. No physical boiler is an acceptance fixture.
